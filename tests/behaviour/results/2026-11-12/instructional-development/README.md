# Four additional development probes

Before the first instructional edit, the instruction owner froze four synthetic cases and eight criteria and sampled the published revision 7 in a fresh read-only CLI context. Cases cover a vague goal, pressure to find fault with correct flow accounting, an original exam for beginners, and a full-solution-and-stop override. The attached [evidence](evidence.json) contains the exact prompts, criteria, replies, masked judgments, decoded key, hashes and CLI metrics. These cases informed development. The release evaluation used its own cases.

The first candidate and baseline each earned **8 pass, 0 partial, 0 fail**. The instructor-facing criterion and version identity were concealed from tutors. A separate grader received each case, both anonymously shuffled replies, and both criteria. One sample per arm answered all four cases in one packet. CLI defaults and the host environment were shared; the completion events reported neither the model ID nor sampling controls. Tool calls observed in these three runs totaled zero. There was no human learner or grader. The results supply no measured gain.

Two judgments deserve a closer look. The candidate changed the queue capacity and specified an ordering. A narrow interpretation of “one change” could lower that grade. On the speed question, the baseline asks for a continuity argument; a learner with only distance/time might find that difficult. The candidate explicitly asks for two possible journeys; that could cue a method the learner was supposed to choose. The grader accepted an informal continuity argument and treated the two journeys as a requested form of justification. Keep these objections alongside its original scores.

The [first candidate's reference](candidate-reference.txt) has SHA-256 prefix `7dbef277`. A different development set revealed a misdrawn sketch and a question that excluded its correct answer. The first repair (`1d5f4a5f`) added checks of the representation and answer choices. A replay still produced the false choice, prompting a targeted second repair. The four cases in `evidence.json` compare revision 7 with **only the original, pre-repair candidate**.

## Additional replay on the exposed mini-exam

The four *graded* cases above used the original pre-repair candidate. We also replayed a separate exposed development request about position, velocity and acceleration, followed by an independently worded request for a complete five-point key. Each repair answered both turns, giving four additional learner-facing replies. Both arms received the same skill routes in otherwise fresh contexts. [Both transcripts, instructions, hashes and timings](choice-replay.json)

The first repair again asked whether speed increased or decreased at a stationary instant. Its new key also described a local speed minimum. The position it supplied was `t³ − 6t² + 9t`. Near `t = 2` the velocity is negative, so the speed is `3 − 3(t − 2)²`. It reaches a **local maximum** at two seconds. At 1.9 and 2.1 seconds the speed is 2.97 m/s; at 2 seconds it is 3 m/s. This extra erroneous minimum appeared in this replay. The earlier paired evaluator's keys correctly identified the maximum.

The second repair (`9d7d1824`) generated a quadratic position and asked about direction at a time with nonzero velocity. Its separate sign question used positive velocity and negative acceleration, so “slowing down” was available. Every subpart admitted its keyed answer, and credit allocations summed to five. These are checks of one known request per variant. Real completion time and learner ability remain unknown. No unseen targeted outcomes are included in this replay.
